## 1. Purpose

Prove exactly which bytes are being certified, so that a later test result can be tied to a revision instead of to a machine state.

Two manifests are required and neither substitutes for the other:

| Manifest | File | What it hashes |
|---|---|---|
| HEAD baseline | `evidence/v12-head-manifest.json` | Git blob bytes of every path in `HEAD` |
| Working tree snapshot | `evidence/v12-working-tree-manifest.json` | Raw bytes of every source/test/doc/config file on disk at freeze time, including modified and untracked files |

Authoritative counts and SHA-256 of both manifests: `evidence/v12-freeze-summary.json`.

## 2. Why two manifests

`HEAD` alone is insufficient: this repository carries a large body of legitimate uncommitted work (modified and untracked files) that is part of what will be tested. Hashing only `HEAD` would certify code that is not on disk.

The working tree alone is insufficient: it cannot prove what the committed baseline was, and it cannot detect accidental loss of tracked content.

## 3. Inclusion rules

**HEAD manifest** — every entry of `git ls-tree -r HEAD`:

- SHA-256 computed over the canonical Git blob content (LF), not the Windows working-tree bytes.
- `core.autocrlf` is recorded in the manifest header for this reason.
- Consequence: a working-tree file that is byte-identical in meaning may hash differently from its HEAD blob on Windows. **Do not use hash equality to decide whether a tracked file is modified — use `git status`.**

**Working tree manifest** — union of:

1. all tracked paths present on disk (`git ls-files`),
2. all untracked, non-ignored paths (`git ls-files --others --exclude-standard`),
3. required ignored test fixtures (see A9).

Each entry carries `status`: `HEAD_IDENTICAL`, `MODIFIED`, `UNTRACKED`, `IGNORED_REQUIRED`, `MISSING`, or `SYMLINK`. There are no submodules and no symlinks in this repository at freeze time (`git ls-files -s` shows zero `160000` and zero `120000` entries).

## 5. Self-exclusion and post-freeze artifacts

A manifest cannot contain its own hash. The manifests are therefore written **after** the source is final, and:

- the manifest JSON files themselves are not entries inside either manifest;
- the SHA-256 of each manifest is recorded in `evidence/v12-freeze-summary.json`;
- the freeze summary cannot contain its own hash either — its hash is recorded in the campaign report.

Any file created **after** the working-tree manifest was generated is listed explicitly in the freeze summary as `POST_FREEZE_ARTIFACT` with its own hash. No post-freeze artifact may be described as part of the certified source.

## 8. Invalidation protocol

The freeze is invalidated immediately if any of the following occurs:

1. any source, test, config, fixture or `.gitignore` change;
2. any new untracked file created under source, tests, docs or evidence;
3. any change to `HEAD`, index contents, or branch;
4. any agent or tool writing into the repository.

On invalidation: declare a new freeze revision, regenerate both manifests, and record the delta. **Never overwrite a previous manifest to make it match a newer tree.**

## 9. What this does not prove

- It does not prove the code is correct; it proves which bytes exist.
- It does not prove ownership of untracked files; that is the disposition review.
- It does not prove a test result is valid unless that result is itself bound to these hashes.
- It does not cover dependency environments, databases or container volumes.
